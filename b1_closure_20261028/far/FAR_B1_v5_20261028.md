裁決順位（衝突時上位勝）：① 對齊 PKG_00～08 → ② Native E2E 自主執行閉環 → ③ 無人值守高自動化 →
④ 高必要性 → ⑤ 不過度治理／不過度工程化 → ⑥ 低阻力、高效率。

## 量測 1：那 18 條不是 18 支程式

```
runner -> coverage
  18  NOT_IMPLEMENTED_EFFECT_TYPED_REFUSAL  RUN-B1-GEN-DISPATCH   ← 全部同一支
   1  EFFECT_IMPLEMENTED  × 12 支不同 runner（含 6 支 native E2E）
```

18 個 `route_id`（`OWNER_REGISTERED::immutable_evidence` … `::golden_sbl`）共用同一個 dispatcher。
所謂「18 條 runner 逐條實作」實際是「18 個 route 的 effect 語義」，不是 18 份程式碼。

## 量測 2：PKG_00～08 與 B1 計畫都沒有要求 30/30

- `FHS_MSC_B1_PIPD_LS_PKG_00…08` 全檢索：無 `30 routes`／`route coverage`／`EFFECT_IMPLEMENTED` 要求。
- B1 計畫的反證標準是**九步各要有真 Raw**（`FHS_MSC_B1_Four_Party_Dogfood_Native_Execution_Plan_r1_1_W18` L728；
  OLD 版 L555 同義），不是 route 覆蓋率。
- 因此 `12/30` 是**本專案自訂的閘門語義**，寫在 `gates.py` 的 residuals 裡。

## 量測 3：1 小時 TTL 不是我挑的，是受制裁工具的上限

`scripts/native-trust-maintenance.ps1:151`：

```powershell
if(-not $plan.approved_files -or $plan.max_ttl_seconds -le 0 -or $plan.max_ttl_seconds -gt 3600 ...
```

提高 `max_ttl_seconds` 就是繞過這支受制裁的 Owner 工具，屬⑤禁止的過度治理繞道。

## 量測 4：18 條若真要做，簽章成本是 1 次解鎖不是 18 次

每列 `executable_path`/`sha256` 都在 `owner_merkle.REQUIRED_FIELDS` 內 → 改動即需重簽該列；
但 `owner_ceremony` 已改成 load-once，一批 30 列 + root = **31 簽章 / 1 解鎖**。逐條做則是 18 次解鎖。

## 量測 5：corpus 走 native 的硬限制

`authorize()` 以 `held_root(request['root'], scope['root_identity'], scope['head'])` 綁定 **單一已認證 root**：

- 所有 request 的 `root` 必須是同一目錄（身分 `32165637:026d000000028a6b`）。
- 交易前後都 `git rev-parse HEAD` 必須等於 `scope.head` → 窗口內 exec repo 不得產生新 commit。
- 因此 corpus 要用 `--sandbox` 指向 exec repo 內的沙箱（`run_case_cli.py --sandbox` 已支援）。
- 244 個 request digest 需在 `scope.request_sha256` 內 → **一次提權寫入**即可（不是 244 次）。

### D1 的具體修法（不動治理、不洗綠）

`gates.py` 的 `_residuals()` 把 `RUNNER_COVERAGE_PARTIAL` 從 **blocker** 改為 **declared_ceiling**：

```json
{"id": "RUNNER_COVERAGE_DECLARED", "value": "12/30",
 "declared_at": "...", "why": "PKG_00..08 未要求 30/30；B1 反證標準為九步真 Raw（計畫 L728）",
 "lifts_when": "release gate 或 owner 明確要求 30/30"}
```

它仍出現在 `residuals`，只是不再單獨把 `mission_complete` 壓成 false——`mission_complete` 的判準回到
conjunction（G-A ∧ G-B ∧ GWO 3/3 ∧ independent audit）＋「無 blocker 級殘餘」。
這是把**自訂指標**降級為**宣告值**，不是把缺口藏起來：數字仍在、理由仍可查、`lifts_when` 明確。

## 建議執行方案（依 D2，共 2 個 owner 動作）

**Phase 1（我，0 owner 動作）**
1. 建 244 個 workorder request（`WO-B1-CASE-<test_id>`，root=exec repo，base_head=目前 HEAD），
   用 kernel 的 `digest_request` 算 digest，寫成 `wave2/corpus_scope_requests.json`。
2. 產 rev 15 計畫：`scope.request_sha256` = 244 digests（其餘不動，含 TTL 3600）。
3. 乾跑：用一次性金鑰 + DB 副本，抽 5 案（首/中/末/2 個負例）跑 `authorize()` 證明全綠。
4. 實作 `wave2/run_corpus_native.py`：對每案 `authorize()` → 成功後才跑該案 → 寫收據。

**Phase 2（owner，1 次 UAC）**：跑 rev 15 的提權腳本（0 解鎖）。

**Phase 3（owner，1 次解鎖）**：console 一次解鎖 → mint 3 references（1h）→ 立刻跑 244 案。

**Phase 4（我）**：DB 端逐案回讀 `canonical_events`、統計 admitted/refused、更新 `STATE.json`/`GATES.json`、
把覆蓋率與 native ceiling 分欄記錄。

風險與停止條件：

- 244 案若在 1h 內跑不完 → 該批只承認已 admitted 的部分，其餘記 `TTL_EXPIRED_NOT_ADMITTED`，不重試、不延長。
- 任一案 `HEAD_CHANGED_BEFORE_COMMIT` → 立即停批（表示有人動了 exec repo）。
- root 身分不符 → 全批拒絕（不是逐案），因為認證是 root 級。

## 明確不做的事

- 不提高 `max_ttl_seconds`、不開 DPAPI escrow、不改 `claim_ceiling`、不 promotion。
- 不把 corpus 的 sandbox 結果宣稱為 native 結果（現況 ceiling 維持 `AUTHOR_SIDE_EXECUTED_SANDBOX`，
  直到 Phase 3 完成）。
- 不為了讓 `mission_complete` 變 true 而刪除或美化任何 residual。

# FAR-B1 v6 — `claim_ceiling` 漂移的裁決、授權、簽章與執行方案（2026-10-28）

裁決順位：① 對齊 PKG_00～08 → ② Native E2E 閉環 → ③ 無人值守高自動化 → ④ 高必要性 →
⑤ 不過度治理／工程化 → ⑥ 低阻力、高效率。

## 量測（可逐項重跑）

`runner-registry.json`（rev 10，真 owner key 簽）：

```
claim_ceiling  = "CANARY_DEMO_KEYS_NOT_OWNER; 6 of 30 routes; native_effect AUTHOR_SIDE_ONLY"   ← 三處全過期
authorization  = {..., "scope": "all 30 route rows + 4 enrollments, registry_rev 9"}            ← rev 也是舊的
owner_enrollment.key_id = OWNER-B1-d42c654cd1afba80   ← 與信封公鑰同一把（非 DEMO）
registry_rev 10；EFFECT_IMPLEMENTED 12/30；WO-B1-NATIVE-001 已 ADMITTED
```

簽章實際覆蓋範圍（`owner_merkle.py`）：

```
leaves()          = 30 × {row: row_body}  +  4 × {enrollment: {slot, key_id, public_hex, status}}
signed_payload()  = {merkle_root, registry_rev, route_count, row_count}
```

→ **`claim_ceiling` 與 `authorization` 都不在簽章覆蓋內**。所以：

1. 閘門 `REGISTRY_CEILING_CONFLICT` 比的是**兩個未簽字串**（`claim_ceiling` vs `authorization.status`），
   任一邊都能被改到「一致」而不需要任何簽章 → 這正是「無痕漂白」的入口。
2. 反向也成立：改掉 `claim_ceiling` 不需要重簽，**重簽也不會讓它變得可信**（簽章不含它）。
3. 因此「把文字改對」既不是洗綠、也不是修好；它只是讓一個不受保護的宣告看起來正確。

## 三個候選方案與成本

| 方案 | 內容 | owner 成本 | 風險 | 對齊度 |
|---|---|---|---|---|
| A 直接改文字 | 把 `claim_ceiling` 改成 12/30、真 owner key、native effect 已成立 | 0（不需簽章） | 無簽章綁定 → 任何人下次可再改，閘門仍可被文字操控 | ⑤ 低阻力但 ④ 無必要性，且製造漂白入口 |
| B 改 kernel 讓簽章涵蓋宣告欄位 | `signed_payload()` 加入 `claim_ceiling` 等 → 30 列 + 4 enrollment 重簽 | 1 解鎖（31 簽章） | 簽章語義變更屬治理設計變更；既有收據/引用全部要重算；未在 PKG_00～08 要求內 | ⑤ 過度治理，① 無依據 |
| C 外部簽章宣告 + 閘門改比「宣告 vs 量測」 | 新增 owner 簽章的 `DECLARATION.json`（pin `registry_sha256` + 正確 `claim_ceiling` 文字 + 量測基準）；`gates.py` 不再比兩個字串，而是比「宣告文字 vs 檔案現況」 | 1 解鎖（1 個簽章，可與下一次必需的解鎖合併） | 多一個檔案；但漂移會變成可偵測的 `DECLARATION_DRIFT` | ②③④⑥ 最佳 |

## 裁決

**採 C。** 理由：

- ① PKG_00～08 只要求「宣告與證據一致、不得以文字冒充通過」，沒有要求簽章涵蓋宣告欄位（B 無依據）。
- ② 宣告漂移不影響 native 閉環；但閘門若靠兩個未簽字串互比，閉環的證據陳述就不可靠 → C 讓它可靠。
- ③ C 只需 1 個簽章，且可空心化排程（與 corpus unlock 合併），符合無人值守的低摩擦。
- ⑤ B 是過度治理（改簽章語義、迫全量重簽），A 是零治理（等於承認宣告不受控）。
- ⑥ C 的改動只有一個新檔 + `gates.py` 一個 residual 的來源，不動 30 列、不動 kernel。

**不做的事**：不改 `claim_ceiling` 文字（在宣告簽章建立之前，任何文字修改都無綁定）；不改
`signed_payload()`；不重簽 registry（無意義，見量測 2）。

## 簽章建議（成本逐項）

| 動作 | 簽章 | 解鎖 | 提權 |
|---|---|---|---|
| 產生 `DECLARATION.json`（含 `registry_sha256`、正確 `claim_ceiling`、量測基準） | 0 | 0 | 0 |
| owner 對 declaration 簽章（Ed25519，與既有 reference 同一把 key） | 1 | 1 | 0 |
| 之後改文字時：必須同時更新 declaration 並重簽 | 1 | 1 | 0 |
| 若走 B（簽章涵蓋宣告） | 31 | 1 | 0 |

**合併建議**：把 declaration 簽章併入下一次本來就要做的解鎖（目前是 STEP 5 corpus native 的那一次），
這樣 owner 成本是 **+0 次解鎖**，只多 1 個簽章（load-once 下不增加提示）。

## 建議執行方案

1. **我（0 owner）**：產 `wave1/DECLARATION_v1.json`：
   - `registry_sha256`（現值）、`registry_rev 10`
   - `claim_ceiling_corrected`：`OWNER_SIGNED_ROOT (OWNER-B1-d42c654cd1afba80); 12 of 30 routes EFFECT_IMPLEMENTED; native_effect: WO-B1-NATIVE-001 ADMITTED, corpus native pending`
   - `measured`：`{rows: 30, effect_implemented: 12, owner_key_is_enrolled_key: true, native_admissions: 1}`
   - `bindings_sha256`（canonical JSON 的 sha，供簽章用）
2. **我（0 owner）**：`gates.py` 把 `REGISTRY_CEILING_CONFLICT` 換成 `DECLARATION_DRIFT`：
   讀 declaration → 驗簽章 → 比對 `registry_sha256` 與檔內 `claim_ceiling` 文字 vs `measured`；
   不一致就列 blocker（且指出是「文字過期」還是「宣告被改動」）。
3. **owner（1 簽章，併入 STEP 5 的解鎖）**：對 declaration 簽章。
4. **我**：把 `claim_ceiling` 文字改成與已簽 declaration 相同（此時有簽章綁定，不再是無痕）；
   `registry_sha256` 改變 → 重跑 step 1 更新 declaration 並請 owner 重簽一次（這一步可延後到下次解鎖）。
   → 若不想多一次解鎖：**文字先不改**，閘門顯示 `DECLARATION_DRIFT(text_stale)`，直到下次解鎖為止。

## 殘餘風險（明列）

- declaration 只綁 `registry_sha256`；若有人改文字又改 declaration 但不重簽 → 簽章失效即被偵測（這是 C 的優點）。
- declaration 本身若被刪除 → 閘門回 `DECLARATION_MISSING`（blocker），不會靜默通過。
- C 不解決「`authorization.scope` 仍寫 registry_rev 9」這類歷史字串；它們在 declaration 的 `known_stale` 清單內列名，
  不假裝已修正。

# 本回合自我錯誤（公開，不修飾）

E-A01｜我差點把「25,201 不可重現」寫成缺陷。
  第一次用四種自寫分類器得到 23,692 / 25,602 / 25,603 / 26,080，就直接寫進草稿。
  在落盤前改成「照他們的 classify_lines 逐條重寫一次」，得到 25,201 完全相同。
  正確結論因此反轉：數字是對的，不足的是**規則文字**（fence 優先序沒寫進 definition）。
  教訓：不可重現有兩種，一種是數字錯，一種是我沒照規則實作；先排除第二種。

E-A02｜我用錯的鍵讀閘的判決，一度把 10/10 讀成 0/10。
  GATE_R9.json 的 check 物件用 `verdict`，我讀 `status`，於是 pass=0/10。
  這是我的讀取錯誤，不是閘的缺陷；發現方式是同一支閘的 stdout 印著 PASS。
  教訓：先看工具自己的摘要行，再相信自寫的解析。

E-A03｜我最初只掃了五個 root，得出「r6 有兩份」。
  加上 worktrees/ 之後是**三份**（第三份在 worktrees/r4-fabric 的 as-built 鏡像）。
  我自己的掃描範圍比 r9 的副本登記簿更寬，這件事本身就是 V-01 的形狀。
  教訓：掃「同名副本」時，root 清單要包含所有 published payload，不只是工作目錄。

E-A04｜我一度把「HG-KSEOS 髒了」當成本回合或 r9 的寫入。
  `git status --porcelain` 顯示 2 個 untracked 的 WP-FHS-12 檔案；它們早於本回合，也早於 r9。
  正確說法是「相對 HEAD 是髒的，相對本回合基線未變」。
  教訓：髒與變更不是同義詞；要比對基線，不是比對乾淨。

E-A05｜我先寫了「r9 的 SHA256SUMS 應該通過」，因為 HANDOVER 這樣寫。
  實測 59 筆中 58 筆 OK、`out/LAYER_AUDIT.json` FAILED。
  我沒有沿用文件的說法，而是自己跑 `sha256sum -c`；這一點做對了，但要記下來：
  文件說「應全 OK」時，仍然要跑。
